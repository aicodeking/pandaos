# boat: self-hosted agent VMs on a dedicated server

> To have a coding agent install the server and connect PandaCode, give it the
> [Agent Setup runbook](../AGENT_SETUP.md).

> **Operator readiness.** Do not offer boat to untrusted tenants until you have done the
> [operator checklist](#operator-checklist) **and** had an external
> penetration test: it has had internal review rounds only, and those kept finding serious bugs (for example,
> a cross-tenant desktop takeover through a same-site websocket). **Architecture & compatibility scope:**
> `boatd` and `boat-api` are **single-host** daemons (no built-in multi-node scheduler, shared control plane,
> or automatic failover); `/api/v1` provides drop-in **`boat.dev` `/api/v1`** compatibility for 98 of 122
> operations (exercised in CI with `boat-sdk` and `@boatdev/sdk`; 24 unsupported routes return `501 not_supported` —
> see [boat.dev API compatibility](#boatdev-api-compatibility-apiv1), and `boat` does **not** implement `e2b.dev`
> SDK/ConnectRPC or Jupyter kernel APIs); CI exercises `boat prompt` with a stub agent (`claude`/Claude Code,
> `codex` and `opencode` are wired for real sessions when API keys are supplied, while `pi`, `prime`, `kimi`
> and `mistral` are CLI-wired from `--help` and untested; see [Agents](#agents)).

## Quick start

1. **Install the server.** Boot `pandaos-v0.2.0-server-x86_64-linux.iso` from the
   [v0.2.0 GitHub Release](https://github.com/AICodeKing/pandaos/releases/tag/v0.2.0) on a dedicated
   host with KVM. Check it with `SHA256SUMS` as described in the [install guide](install.md#1-get-the-iso).
   For a trusted single-owner host, run the command below with the confirmed disk and your own
   domain and key. Reboot, then run `sudo nixos-rebuild switch --flake /etc/pandaos#pandaos`.
   Set up [DNS](#dns-records) for your chosen domains. The
   [install section](#install-on-a-dedicated-server-hetzner-ovh) covers the data disk, multi-tenant
   setup and TLS.
   ```sh
   sudo panda-install --profile server --disk /dev/nvme0n1 --domain boat.example.com \
     --untrusted-tenants false --ssh-key "ssh-ed25519 ..."
   ```
2. **Install guest images.** Follow [Guest images](#guest-images) to verify and import the kernel
   and one root filesystem.
3. **Get the owner key.** `sudo boat-admin init -user me -team ops >/dev/null` writes the bare
   `boat_...` token to `/root/boat-owner-token` (mode 0600). Transfer it to your password manager
   in a private terminal and delete the temporary file once it is stored.
4. **Point boat.dev's SDK at it.** Use `https://api.boat.example.com/api/v1` as the base URL and
   read `TOKEN` from your secret manager.
   ```python
   from boat_sdk import ApiClient, BoatApi, Configuration
   from boat_sdk.models.create_sandbox_request import CreateSandboxRequest
   api = BoatApi(ApiClient(Configuration(host="https://api.boat.example.com/api/v1", access_token=TOKEN)))
   sid = api.create(create_sandbox_request=CreateSandboxRequest(name="first")).sandbox.id
   ```
   ```ts
   import { BoatApi, Configuration } from "@boatdev/sdk";
   const api = new BoatApi(new Configuration({ basePath: "https://api.boat.example.com/api/v1", accessToken: TOKEN }));
   const { sandbox } = await api.create({ createSandboxRequest: { name: "first" } });
   ```
   The spec those SDKs are generated from is served at `https://api.boat.example.com/api/v1/openapi.json`
   (also `/openapi.json` and `/openapi.yaml`). For the CLI, install this repo's `boat` from the
   release or [build it from source](../components/boat/cli/README.md). It takes
   boat.dev's verbs and flags and accepts the `/api/v1` URL. boat.dev's own CLI binary is not tested
   against this server.
5. **First sandbox from the CLI.** Download `boat_<os>_<arch>` (with `.exe` on Windows) and
   verify it with `boat_SHA256SUMS`, or use the [installer in the runbook](../AGENT_SETUP.md#b4-create-the-first-owner-key-and-test-one-vm).
   Use a private terminal for the signed port URL, and feed the login key from your secret
   manager through stdin.
   ```sh
   boat login --url https://api.boat.example.com --key-stdin
   boat new --name first --no-auto-stop     # prints the sandbox
   boat exec current -- uname -a
   boat host current 3000                   # a token-gated https URL for port 3000
   boat delete current --yes
   ```

`boat` turns one dedicated server into a self-hosted alternative to boat.dev.
Each agent gets a persistent Firecracker microVM, and you get an API, a CLI,
SDKs, a web dashboard, ssh, port URLs, a browser desktop, forks and snapshots. The server
profile (`nixos/profiles/server.nix`) is headless PandaOS with
`services.boat.enable = true`.

| Part | Where | What it does |
|---|---|---|
| `boatd` | `components/boat/boatd` | Root VM manager: Firecracker + jailer, bridge `boatbr0`, `10.200.0.0/16` NAT, nftables tenant isolation, snapshots. Writes `/run/boat/routes.json`. |
| `boat-api` | `components/boat/api` | REST API on 127.0.0.1:8740 (keys, teams, secrets, webhooks, metering, link minting). User `boat`. |
| `boat` | `components/boat/cli`, `sdk` | CLI (`--json` everywhere) and the Python/TypeScript SDKs. |
| guest | `components/boat/guest` | Ubuntu 24.04 rootfs + kernel with `boat-agent`; the `full` image adds a KasmVNC desktop on guest port 6080. |
| gateway | `components/boat/gateway` | Caddy (TLS), `boat-gateway` (port routes, desktops; its own uid, no access to boatd), the ssh jump host, and the static dashboard at `https://api.<domain>/`. |
| module | `components/boat/module.nix`, `ops.nix` | NixOS options and units: the above plus reboot detection, the maintenance window (boatd restart or reboot), backups. |

## Operator checklist

Before you hand out API keys:

1. **Hardware with KVM.** `ls /dev/kvm` in the rescue system. Without it, boatd refuses to start (`boatd: /dev/kvm is missing ...`, exit 78, no restart loop).
2. **Separate domains for tenant content.** Pick a base domain (`boat.example.com`) and a **different registrable domain** for what tenants control: `vmDomain` (port routes) and `desktopDomain` (desktop pages), e.g. `boatvms.example.net` and `desktop.boatvms.example.net`, or names under a suffix on the [Public Suffix List](https://publicsuffix.org/). With the defaults (`vm.<domain>`, `desktop.<domain>`) a tenant's page is same-site with `api.<domain>` and can set cookies on the parent domain. A rebuild warns about this until you fix it. Tenants' origins are always same-site with each other unless the VM domain is on the PSL. The gateway's Origin checks cover requests, and it drops `Domain` from every `Set-Cookie` a tenant app sends, but it cannot see a page's own `document.cookie`, so a tenant's script can still set a cookie on `vmDomain` that reaches sibling tenants. **Only a `vmDomain` on the PSL stops that; adding it is your job, no code here can.**
3. **DNS** (see below), including both wildcards.
4. **TLS with DNS-01.** Set `gateway.dnsProvider` and a matching Caddy DNS plugin. On-demand HTTP-01
   lets tenants exhaust the Let's Encrypt limit and block new certificates for everyone. The
   installer's `gateway.allowOnDemandTLS = true` fallback is for a trusted host. For multi-tenant
   use, configure DNS-01 before rebuilding.
5. **Backups.** Set `services.boat.backup` to a restic repository you control, keep the repository password off the box, and keep an offline copy of both sealed keys (see "Secrets"). A backup alone does not restore secrets on a new host. Test a restore.
6. **Maintenance window.** Turn on `services.boat.maintenance.reboot` (default: Sunday 04:00, only when something is pending): with `action = "auto"` (the default) it restarts only boatd when nothing but boatd or Firecracker changed and reboots for anything else, such as a kernel; `action = "reboot"` always reboots. Or watch `boat_reboot_pending` and act by hand.
7. **Abuse policy.** You are the hosting provider for everything your tenants run: public port URLs, outbound traffic from your IPs, mail, scanning and mining. Publish an acceptable-use policy, keep `abuse@` working for your provider (Hetzner and OVH forward complaints and can null-route the server), keep team quotas tight (defaults: 10 running VMs, 50 total, 32 vCPU, 64 GiB RAM, 1000 GiB disk, 100 snapshots, 50 routes), and give keys only to people you trust. boatd drops outbound SMTP (25/465/587) unless `boatdSettings.allowSMTP = true`, and can cap each VM's egress (`boatdSettings.egressMbit`).
8. **Monitoring.** node-exporter is on :9100 (not opened in the firewall). It includes the textfile metric `boat_reboot_pending`. Usage per team is at `GET /v1/usage`; `from`/`since` and `to` take RFC 3339 or a date-only `YYYY-MM-DD` (UTC). A date-only `to` means the end of that UTC day (the next midnight, exclusive), so `from=2026-01-02&to=2026-01-02` is that one day; an RFC 3339 `to` is exact. `to` must be after `from`. Per-sandbox `GET /v1/vms/{id}/usage` and compat `…/usage` take RFC 3339 (compat: or unix seconds) only.
9. **External penetration test** before untrusted tenants. Nobody outside this project has reviewed it.

## Install on a dedicated server (Hetzner, OVH)

1. Boot the server ISO (Hetzner: virtual ISO in the Robot console or KVM-over-IP; OVH: IPMI).
2. Run:
   ```sh
   panda-install --profile server --disk /dev/nvme0n1 --data-disk /dev/nvme1n1 \
     --domain boat.example.com --acme-email ops@example.com \
     [--ipv6-prefix 2a01:4f8:xxx:yyy:b0a7::/80] --ssh-key "ssh-ed25519 ..."
   ```
   `--data-disk` erases the second disk and formats it as btrfs (`PANDADATA`) for `/var/lib/boat`. It is pinned by UUID as a required mount in `/etc/pandaos/disk.nix` and recorded in `/etc/pandaos/data-disk`. If that disk is ever missing, boatd and boat-api refuse to start rather than write VM data to the system disk. Without `--data-disk`, `/var/lib/boat` is a btrfs subvolume on the system disk. VM disks are reflink copies either way, so fork and snapshot are near-free. To mirror later: `btrfs device add` + `btrfs balance start -dconvert=raid1 -mconvert=raid1`.
   Use the `iso-server` ISO: the other ISOs do not carry the server system.
   Confirm the exact disk paths with `lsblk` before running the installer.
   `--acme-email` is optional: without it Caddy registers its ACME account with no e-mail.
   Add `--untrusted-tenants false` on a trusted single-owner host. For multi-tenant use, configure
   separate tenant domains and DNS-01 before the post-install rebuild. On a `--build` install,
   configure them before running the installer.
   No ISO or console, only ssh into the provider's OS (Hetzner's default Ubuntu, a rescue system)?
   Install over ssh with kexec and `--build`; see [install.md](install.md#hosted-server-over-ssh-kexec).
   On hosts without DHCP (static addresses), use `--build` so the network settings apply from the first boot.
3. Reboot, log in, and add any further settings to `/etc/pandaos/local.nix`. The example below
   uses separate tenant domains, DNS-01 and declarative guest images:
   ```nix
   services.boat = {
     vmDomain = "boatvms.example.net";
     desktopDomain = "desktop.boatvms.example.net";
     # Hashes: boat_guest_SHA256SUMS on the release page. "slim" also exists.
     images."ubuntu-24.04/vmlinux" = {
       url = "https://github.com/AICodeKing/pandaos/releases/download/v0.2.0/boat-guest-vmlinux"; sha256 = "...";
     };
     images."ubuntu-24.04/rootfs.ext4.zst" = {
       url = "https://github.com/AICodeKing/pandaos/releases/download/v0.2.0/boat-guest-rootfs-full.ext4.zst"; sha256 = "...";
     };
     gateway.caddyPackage = pkgs.caddy.withPlugins {
       plugins = [ "github.com/caddy-dns/cloudflare@v0.2.1" ]; hash = "sha256-...";
     };
     gateway.dnsProvider = "cloudflare {env.CF_API_TOKEN}";
     gateway.environmentFile = "/var/lib/secrets/caddy-dns.env";   # CF_API_TOKEN=...
     backup = {
       enable = true;
       repository = "sftp:u123@u123.your-storagebox.de:/boat";
       passwordFile = "/var/lib/secrets/restic-boat.pass";
     };
     maintenance.reboot = true;
   };
   ```
   Merge the settings into the existing module. Add `pkgs` to the module arguments
   (`{ lib, pkgs, ... }:`) for the Caddy example. Replace the example hashes and remove
   the installer's `services.boat.gateway.allowOnDemandTLS = true` line when adding DNS-01.
4. Apply the settings:
   ```sh
   sudo nixos-rebuild switch --flake /etc/pandaos#pandaos
   ```
5. After installing guest images, use the [quick start](#quick-start) to create the owner key
   and log in. `boat-admin init` supports `--token-file PATH` for an alternate token file.

### Guest images

Get the kernel and one root filesystem. The default image goes in
`/var/lib/boat/images/ubuntu-24.04/{vmlinux,rootfs.ext4}`. boat-api offers `ubuntu-24.04`
when `services.boat.images` is empty.

- **GitHub Release.** From [v0.2.0](https://github.com/AICodeKing/pandaos/releases/tag/v0.2.0),
  download `boat-guest-vmlinux`, `boat-guest-rootfs-full.ext4.zst` or
  `boat-guest-rootfs-slim.ext4.zst`, and `boat_guest_SHA256SUMS`. Run
  `sha256sum -c --ignore-missing boat_guest_SHA256SUMS` and confirm that both files report `OK`.
- **CI artifact (no local build).** With repository access, run `gh workflow run release.yml -R AICodeKing/pandaos`
  and use `gh run download <run-id> -R AICodeKing/pandaos -n boat-assets` when the dry run completes.
  It builds the same guest filenames, keeps them for seven days and includes `boat_guest_SHA256SUMS`.
  Verify the images with that manifest before installing.
- **Build:** on any x86_64 host with Docker, `components/boat/guest/build.sh all` writes `out/vmlinux` and `out/rootfs-{slim,full}.ext4.zst`.
- **Then install:** `sudo boat-admin images import boat-guest-vmlinux boat-guest-rootfs-full.ext4.zst` (a `.zst` is decompressed; a plain `.ext4` is copied with a reflink when it can be). It checks the rootfs is a clean ext4 image before replacing anything, installs both files 0644 as `ubuntu-24.04` (the default id while nothing is declared) and needs no restart: VMs created after it use the new files, running ones keep theirs. `--id NAME` installs another image; declare it with `services.boat.localImages = [ "NAME" ];` so boat-api offers it (boat-admin prints that line). `sudo boat-admin images list` shows what is installed and whether it is declared. `boat-images.service` logs the import command while the default image is missing. Or put the files on any HTTPS server you control and set `services.boat.images` to those URLs with the hashes from `boat_guest_SHA256SUMS`. `boat-images.service` fetches only `https://` URLs and checks every hash.

Use `full` for the desktop; on `slim`, `POST …/desktop` answers 422 `not_supported`.

### DNS records

| Name | Type | Value |
|---|---|---|
| `api.boat.example.com` | A / AAAA | server |
| `desktop.boat.example.com` (default `desktopDomain`) | A / AAAA | server |
| `*.desktop.boat.example.com` (default wildcard) | A / AAAA | server (one origin per VM desktop) |
| `ssh.boat.example.com` | A / AAAA | server |
| `*.boatvms.example.net` (= `vmDomain`) | A / AAAA | server (port routes `<port>-<vmid>.<vmDomain>`) |

For a custom `desktopDomain`, point both that name and its wildcard at the server.

### TLS

- **Wildcards via DNS-01 (recommended).** Set `gateway.dnsProvider` and use a Caddy build with the matching [caddy-dns](https://github.com/caddy-dns) plugin. Caddy then gets `*.<desktopDomain>` and `*.<vmDomain>` certificates, so the provider must manage both zones. New VMs and ports work instantly, and their names stay out of Certificate Transparency logs.
- **HTTP-01 fallback, not for production.** Set `gateway.allowOnDemandTLS = true`. Caddy then gets one certificate per desktop and per port URL on the first request, after asking boat-gateway (127.0.0.1:8743) whether that host is live. The costs: a few seconds' wait on first use; every name is published in CT logs; and Let's Encrypt's limit of 50 certificates per registered domain per week is shared, so **tenants creating routes can stop new certificates for everyone**. boat-gateway approves at most 10 new hostnames per team per day (`-ask-team-limit`, `-ask-window`) and 40 across all teams per week (`-ask-global-limit`, `-ask-global-window`), below that 50; previous approvals do not consume quota again. The approvals are kept in `/var/lib/boat-gateway/cert-quota.json` (`-ask-state`), so a gateway restart does not reset the count. `quotas.maxPorts` and these caps limit the damage but do not remove it: once the week's 40 are used, new desktops and port URLs get no certificate until the window moves on.

### IPv6 subnet routing

- **Hetzner** routes a `/64` to the server. Give VMs a sub-prefix such as `2a01:4f8:a:b:b0a7::/80` and keep `::2` on the uplink; no NDP proxy is needed.
- **OVH** puts the `/64` on-link. Either have it routed, or use NDP proxying (`proxy_ndp=1` + `ip -6 neigh add proxy`, or `ndppd`). The module sets `accept_ra=2` so the uplink keeps taking RAs while forwarding.
- **Extra IPv4:** route the addresses to the server and list them in `publicIPv4Pool`; boatd maps them 1:1 to VMs.

## Sizing

The default sizes are `small` 2 vCPU/4 GiB, `default` 4/8, `large` 8/16 and `xlarge` 16/32, with sparse disks. The default team quota follows `services.boat.untrustedTenants`, which the server profile turns on by default: 10 VMs / 32 vCPU / 64 GiB per team; with `untrustedTenants = false` (a host whose tenants are all trusted) it is 0, no per-team cap, and host admission alone bounds a team.

- **RAM** is the primary active-VM limit in `untrustedTenants` (`memOvercommit = 1.0`, no overcommit): each active VM counts its guest RAM plus `vmOverheadMiB` (256 MiB, so 8,448 MiB per `default` VM) against `MemTotal - hostReserveMiB` (1,024 MiB). Trusted hosts (`untrustedTenants = false`) default to `memOvercommit = 1.5`.
- **Stop time.** On stop or reboot, boatd writes every running VM's memory to disk. `services.boat.stopTimeoutSec` (default 900 s) must cover the total RAM of running VMs divided by the disk's write speed. That is about 128 GiB at 1 GB/s ≈ 2-3 min, so 900 s leaves room.
- **CPU** can be overcommitted about 2-4x for agent workloads, which mostly wait on LLMs (`cpuOvercommit = 4.0`; `untrustedTenants` disables SMT via `nosmt=force`, halving logical threads).
- **Disk and `io_uring`.** Deduct ~15% from raw NVMe capacity (`boatd` `minFreePct = 10` free-space floor plus ~5% for OS, ~3 GB base guest images and btrfs metadata). Under `untrustedTenants` (`storageOvercommit = 1`), every running or stopped `default` VM reserves its full nominal 51 GiB disk + 8 GiB memory snapshot (~59 GiB) against usable storage; under `untrustedTenants = false` (`storageOvercommit = 10`), stopped VMs consume only their written blocks + memory snapshots (~3.4 GiB measured). In `untrustedTenants` mode, Firecracker keeps `Async` (`io_uring`) disk I/O enabled by setting `kernel.io_uring_disabled = 1` and `kernel.io_uring_group` to `jailGid` (`boat-vmm` in `nixos/profiles/server.nix`, `boat-fc` in `bench/boatbench/stack.sh`), blocking unprivileged host processes from `io_uring` without forcing VMMs back to `Sync` (which is used only when `jailGid` is unset).
- **Example:** an AX102 (16 cores, 128 GB, 2x1.92 TB NVMe, ~1,519 GiB usable tenant storage on a mirror) admits **15** `default` VMs at once in `untrustedTenants` mode (**22** in trusted `1.5` mode) and holds **25** total running+stopped VMs under `storageOvercommit = 1` (or hundreds stopped in trusted mode). On a single-NVMe AX42 (8 cores, 64 GB, `476 GiB` raw / `404 GiB` usable), `boatd`'s `hostStorageCheck` checks raw partition capacity (`⌊476 / 59⌋ = 8` nominal VMs) so all **7** RAM-bound `default` VMs boot while disks stay sparse, whereas live `minFreePct = 10%` (`checkFloor`) caps worst-case 100%-full 59 GiB disks at **6** VMs (see [`cost.md`](cost.md)).

## Gateway design

```
Internet --443--> Caddy --api.D-----------------------> boat-api :8740 (/internal/* -> 404)
                        --desktop.D/<id>?sig----------> boat-gateway: 302 -> <id>.desktop.D (sets nothing)
                        --<id>.desktop.D--------------> boat-gateway --> <vm ip>:6080 (guest token proxy)
                        --<port>-<id>.<vmDomain>------> boat-gateway --> <vm ip>:<port>
         --2222--> sshd (user jump only) --direct-tcpip, permitopen--> <vm ip>:22
```

- **One origin per VM.** Each desktop is `<id>.desktop.D` and each port route is `<port>-<id>.<vmDomain>`. Session cookies are `__Host-` prefixed: host-only, `Secure`, `Path=/`, `HttpOnly`. Browsers refuse a `__Host-` cookie that carries a `Domain`, so a page on another VM's origin can neither read nor plant one. Desktop cookies are `SameSite=Strict`. A browser withholds a Strict cookie on the redirects of a navigation that began on another site, so for `Sec-Fetch-Site: cross-site` the gateway answers with a small same-origin page that starts a fresh navigation; everything else gets a 302. Every VM's credential is bound to its id by the HMAC: VM A's cookie or link gets 401/403 on VM B's origin. This is checked in the e2e.
- **Origin checks.** All VM origins are same-site with each other, so `SameSite` does not stop a page on VM A from sending B's cookie along, for example on `wss://<B>.desktop.D/`. The gateway therefore refuses (403) a desktop request whose `Origin` is not exactly its own origin, any desktop request marked `Sec-Fetch-Site: same-site` or `cross-site` unless it carries a signed link, and framing (`frame-ancestors 'self'`). A private port route accepts its cookie only from its own origin or another port of the same VM, and from top-level navigations; a program sending `X-Boat-Route-Token` is not limited, since it holds the token itself. Consequence: `<img>` or `<script>` from one private port of a VM to another is refused, so use relative paths or a public port. Desktops cannot be embedded in an iframe on another origin.
- **Dashboard.** Static files from `components/boat/dashboard/web`, served from the read-only Nix store at `https://api.D/`, on the same origin as the API, with a strict CSP (`default-src 'self'`, no framing). `/v1/*`, `/api/v1/*` (boat.dev-compatible, for its official SDKs) and `/healthz` go to boat-api; `/internal/*` is 404. It holds the user's API key in the browser, which is why it is never on a tenant-controlled origin.
- **Desktop links.** `GET /v1/vms/<id>/desktop` returns `https://desktop.D/<id>?exp&sig` (sig = `hex(HMAC-SHA256(Kdesktop, "<id>.<exp>"))`, 5 min by default). The gateway 302s it to `https://<id>.desktop.D/?exp&sig`, which checks the signature, sets `__Host-boat_gw` and drops the signature from the URL. Toward the guest, the gateway removes the client's `boat_*`/`__Host-boat_*` cookies and sends `boat_desktop=hex(HMAC(Kguest, "guest-desktop.<id>"))`. boat-api starts the guest desktop with that same token.
- **Port routes are private by default.** A route needs a token: `token = <exp>.hex(HMAC(Kroute, "route.<port>-<id>.<exp>"))`, minted by `GET /v1/vms/<id>/ports/<port>/url` (`boat ports url VM PORT`). Programs send it as `X-Boat-Route-Token`; browsers open `…/?boat_exp&boat_sig` once, which sets the host-only `__Host-boat_route` (SameSite=Lax). A port is reachable without a token only if added with `--public`, which boatd lists in routes.json `"public"`. When the list is missing, routes stay private (fail-closed). Tokens and cookies never reach the VM.
- **One HMAC key per purpose.** The shared key file (`-desktop-key-file` / `-desktop-key`) is a master key that signs nothing itself: `Kdesktop`, `Kroute` and `Kguest` are `HMAC-SHA256(master, "boat-hmac-v2/desktop-link" | "…/port-route" | "…/guest-desktop")`, derived the same way by boat-api (`PurposeKey`) and boat-gateway, so a token of one kind never verifies as another, whatever its payload. **Migration:** before this, all three were signed with the master key, told apart by payload prefixes. After the upgrade boat-api mints only per-purpose tokens; the gateway still accepts a master-key token that expires within its legacy window (`-legacy-hmac-until`: an absolute unix time; disabled by default, and `0` or `-1` also mean never, so a restart never reopens it; set it explicitly, e.g. to upgrade time + 8 days, only while migrating pre-split tokens), and during that window also sends the guest desktop both cookies, so a desktop started before the upgrade keeps working until its next `GET …/desktop` restarts it with the new token. After the window, master-key tokens are refused. Nothing needs to be done by hand. CI: `TestPurposeKeysAndLegacyWindow` (gateway), `TestFilesSSHDesktop` (boat-api), and `gateway/e2e-edge.sh` (a desktop-link-key token is refused as a route token, a pre-split token still works inside the window).
- **Revoking port and desktop links.** A port token lives up to 7 days. `POST /v1/vms/<id>/port-tokens/revoke` bumps the VM's route generation to revoke every existing token, link and cookie for its private ports and desktop, and so does removing a port. Deleting an API key, or removing a member (whose keys go with them), does the same for every VM that key minted a private or desktop link of, and no link outlives the expiry of the key that minted it; a port token minted afterwards signs `route.<port>-<id>.g<gen>.<exp>`.
  With gateway `-api` configured (as in NixOS), boat-gateway fetches boat-api's loopback-only `/internal/route-gens` with a 1 s timeout, waiting 2 s between background fetches. Revocation is asynchronous: older generations are rejected once a newer snapshot arrives, and a newly minted token can get 401 until its generation is fetched. A validated snapshot expires 5 s after the successful fetch's **request start**, so a slow response consumes that budget. Failed or invalid responses, including HTTP 404, neither replace the last good snapshot nor renew its freshness.
  When the snapshot is missing or stale, private-port and desktop requests retry a fetch once, then fail closed with 503 if no fresh snapshot is available. Desktop-host TLS `ask` checks likewise retry and deny approval (404) until a fresh snapshot confirms a minted desktop link. Public port routes do not depend on this snapshot. Without gateway `-api`, revocation tracking is disabled and no snapshot is required.
- **Tenant cookies.** The gateway removes the `Domain` attribute from each `Set-Cookie` in a guest's response, so the cookie stays on that VM's own host. See checklist item 2 for what it cannot remove.
- **Live routes.** boat-gateway (Go stdlib, websockets included) re-reads `/run/boat/routes.json` whenever its mtime or size changes, so new VMs and ports never reload Caddy.
- **SSH:** OpenSSH ProxyJump.
  ```sh
  boat ssh <vmid>                                    # ProxyCommand ssh -W via the jump host
  ssh -J jump@ssh.boat.example.com:2222 dev@10.200.x.y
  ```
  Port 2222 admits only the system user `jump`. It has no password, shell, tty, agent, X11 or socket forwarding (`ForceCommand false`). `/etc/boat/jump-keys`, run as the dedicated unprivileged `boat-ssh` user, asks boat-api's loopback-only `POST /internal/ssh/authorize` about the offered key. It emits only validated `restrict,port-forwarding,permitopen="<literal IPv4>:22"` lines for currently committed live grants and ready VM identities. The guest also checks managed keys online through `POST /v1/vms/{id}/ssh/authorize`, using a separate root-protected lookup credential. No static jump file, routes-file liveness check, cached allow, or offline fallback authorizes managed SSH. An unavailable API, unready policy, malformed response, or lookup timeout denies new managed authentication.
  sshd authorizes a key once per connection, so open jump sessions are also re-checked: `jump-keys` records which sshd connection each authorization belongs to (under `/run/boat-jump/`, login denied if it cannot record), and the root `boat-jump-reaper` service re-asks boat-api every 3 s and terminates a connection when its key no longer authorizes anything, or when a target it was granted is withdrawn while a VM is still at that address (a revoked per-VM grant, or the address reused by another VM); a teammate merely stopping or deleting a VM does not end it. Without an answer from boat-api it is kept for at most 2 min, then killed. The reaper stamps a heartbeat each pass and `jump-keys` refuses logins when it is older than 30 s, so a dead reaper cannot leave sessions unrevoked. `Match User jump` also sets idle limits (`ClientAliveInterval`, `UnusedConnectionTimeout`, `ChannelTimeout`, `MaxSessions 2`). See [security.md](security.md).

  Grants record their issuing key and user. Revoking or expiring that key, removing the member, or explicitly revoking the grant denies subsequent managed authorization decisions. `GET /v1/vms/{id}/ssh` (`boat ssh-keys ls <vm>`) lists grants; `DELETE /v1/vms/{id}/ssh/{fingerprint}` (`boat ssh-keys rm <vm> FINGERPRINT`) revokes one, a member only their own, an admin any. Historical unowned grants are quarantined debt: they cannot authorize managed SSH and need explicit re-enrollment. Durable VM self-grants retain their committed lifetime across self-token generation and SSH issuance-policy changes; new issuance must satisfy the current credential and policy. Stopped, expired, deleted, pending or unready VMs cannot authorize a new managed login.

  The boundary is the API's fenced allow decision. A decision made before revocation can reach sshd afterward; already authenticated SSH sessions and existing jump transports/channels are not terminated by grant revocation. Guest root and explicitly enrolled tenant keys in `authorized_keys.tenant` are independent authority outside managed revocation. Unknown legacy `authorized_keys`/`authorized_keys2` bytes are archived with protected permissions, never silently treated as tenant enrollment.

### Managed SSH migration

Perform the coordinated API, boatd, guest-policy and jump-helper upgrade in a maintenance window with external VM ingress closed and access suspended. Keep SSH, forwarded guest traffic, IPv6 ingress and existing pre-authentication connections closed while installing and verifying policy; stop old sshd/socket listeners and terminate old pre-authentication handlers before releasing access. Restart or reconcile every VM under a fresh host boot epoch and verify its guest helper/config digest and readiness before restoring its routes and ingress. A failed installation, verification, firewall update or route update leaves the VM quarantined.

Inventory legacy key files before migration. Keep unknown bytes in a root-protected archive for operator review and explicitly re-enroll intended tenant keys into `authorized_keys.tenant` or managed grants through the API. Do not promote the archive, unowned grant records, or old jump key files into authorization. The canonical guest artifact is `components/boat/guest/ssh-authorize.py`, passed to boat-api with `-ssh-policy-helper-file`; lookup configuration is independent of tenant environment overrides such as `BOAT_API_KEY`. Managed guest SSH requires a reachable HTTPS API and trusted certificate chain.

Keep ingress closed if any slice is missing or verification fails. Rollback must preserve online authorization and quarantine; never restore the old static key policy. Existing authenticated sessions require a separate operator teardown when immediate session termination is needed. This deployment procedure requires integrated guest, sshd and network verification; local helper mocks alone do not establish whole-system readiness.

## Security model

- **VM isolation.** Each VM is a KVM guest run by Firecracker (a minimal Rust VMM) inside the jailer: its own uid/gid (from 900000), a chroot, a mount namespace, its own cgroup under `boat-vms`, outside `boatd.service`, so a boatd crash spares the VMs, and seccomp. A guest root exploit must escape KVM, then the jailed, unprivileged Firecracker process.
- **Tenant network isolation and quarantine.** Every VM has its own tap on `boatbr0`. Until a VM's guest SSH policy is attested over Firecracker vsock for the current boot epoch (`sshNetworkReady()`), `quarantineRules` at the top of `inet boat` `input`, `forward` and `output` (before `established,related` or DNAT) and L2 drops in `bridge boat` block **all** IPv4 and IPv6 traffic with zero exceptions, while `/run/boat/routes.json` omits the VM's routes and lists its IP under `"quarantined"` (rejected with HTTP 403 by `boat-gateway`). Once unquarantined, nftables drops tap-to-tap traffic except within a team that has `allowIntraTeam`, and NAT is outbound only. From an unquarantined VM, the host answers only DNS on the bridge address, the AI proxy port, `hostHttpsPort` restricted to `hostHttpsAddrs` (or local non-loopback/non-Tailscale/non-link-local addresses when `hostHttpsAddrs` is unset) and ICMP (`boatd/netw.go`); everything else addressed to the host from `boatbr0` is dropped, including 80/22/2222.
- **Web isolation.** Every VM's desktop and every port route has its own origin and host-only `__Host-` cookies, and credentials are HMAC-bound to the VM (and port). Port routes are private by default. With a separate registrable `vmDomain`, tenant apps cannot touch `api.`/`desktop.` cookies either. `api.D` uses bearer tokens, not cookies.
- **Host services.** boatd is the only root daemon. boat-api runs as `boat`; boat-gateway, which faces the internet, runs as its own `boat-gateway` with no access to boatd's socket (0660 `root:boat`, in a 0751 directory) or to boat-api's data. Both have no capabilities, `ProtectSystem=strict`, a syscall filter and MemoryDenyWriteExecute. `/internal/*` is never published. boatd and boat-api have `OOMScoreAdjust=-900` and each Firecracker 500, so the host OOM killer takes a VM before them. boatbr0 never accepts IPv6 router advertisements, so a VM cannot reconfigure the host. Firecracker is pinned to the release e2e tests (v1.17.0).
- **Disks a team did not build.** A VM from an imported or shared snapshot, or from a fork or snapshot of such a VM, runs that disk's init before anyone can look at it. So it gets **no team secrets** unless the create request names them in `secrets`, which needs the `exec` scope (such a key could read them from any VM anyway); an environment's secret selection does not count, at create, start/resume or fork (a named environment gives such a VM its vars only and never changes its selection). It also starts blocked at the AI proxy, and with the proxy off it gets no raw keys; `PUT /v1/vms/<id>/ai-access` opens it. The mark is recorded when the VM is created, so VMs made before this rule are not marked.
- **`noEnv` is sticky (boat.dev's).** A sandbox created, started or forked with `noEnv` stays `noEnv` for the rest of its life: it is marked when the `noEnv` create, start or fork takes effect (`no_env_run: true` on native VM bodies; the mark is persisted, so it survives a stop, a plain start or resume, a type change, a recover and a restart of boat-api). Every later start is a `noEnv` start: no team secrets are pushed, the old secret selection is not restored, the stored per-sandbox `env` is not replayed (see below), and a prompt or command gets none. A fork, a clone and a create from a snapshot of such a sandbox is `noEnv` too (a snapshot taken from a `noEnv` sandbox is recorded `@no_env`; one taken before the sandbox became `noEnv` is not, and a create from it follows its own record). A **start or fork that names an `environment`, or sends `no_env: false`, on a `noEnv` sandbox is refused with 400 `no_env_sticky`** before anything is stopped, started or copied; the message tells the caller to create a new sandbox (a create from a `noEnv` snapshot that names an `environment` or a non-empty `secrets` list is refused the same way). A `noEnv` create (or a create from a `noEnv` snapshot) that names a non-empty `secrets` list is 400 `no_env_sticky` as well, before anything is created: `secrets` absent or `[]` is fine, and a `noEnv` sandbox never holds a team secret. A snapshot is recorded `@no_env` only when the run it was taken from pushed no team secret (the run's recorded secret names are empty); a run marked `noEnv` whose names are not empty, or unknown, is never recorded as secret-free (recorded by its names, or not at all), and a share to another team carries only a genuine `@no_env` record. A `noEnv` mark is rolled back only when the start that would have set it failed closed (the previous state stands), and ends with the sandbox's deletion. A marked sandbox is started with `fresh_boot` only the first time (when its previous run may have had secrets); later starts resume its memory, which holds none. **Stored env.** A `noEnv` start or fork uses only the `env` sent on that request: the `env` stored for the sandbox (and a parent's, for a fork) is not replayed to it, and the request's own `env` is not stored. See also "A `noEnv` sandbox's own token" below and `docs/security.md`.
- **`noEnv` runs and AI keys.** A `noEnv` run (start, restart, prompts, a fork child) never gets a raw AI provider key, even with the team's AI proxy off (a raw key cannot be revoked per VM); with the proxy on it keeps its per-VM proxy token. `noEnv` withholds team secrets, not AI access: a `noEnv` run still gets AI proxy tokens, so the team's AI credit can be spent from it (unchanged).
- **What a share gives away.** A snapshot holds the VM's disk, including `/etc/boat/env`. Creating a share moves the source VM to a new AI proxy token, so the token on the snapshot is dead; processes already running in that VM keep the dead token until they restart. Team secrets on the disk and raw AI keys (proxy off) go with the share and cannot be taken back: revoke them at their issuer.
- **In-flight limits.** Per team, at most 64 open exec, SSE, log and download streams (`-team-streams`), 8 file uploads and imports (`-team-uploads`), and 128 requests of any kind (`-team-inflight`); the `/api/v1` file routes hold the same slots as their `/v1` twins. Signed-link downloads count separately from the team's. Per VM, at most 16 AI proxy requests (`-ai-vm-inflight`). Past a limit the API answers 429.
- **Request bodies.** A body sent to a VM route (`/v1/vms/{id}/…`, `/api/v1/sandboxes/{id}/…`) is read only after the VM's ownership check, so another team's VM costs boat-api no memory. On every route that is not a stream or an upload the body must arrive within `-body-timeout` (30 s). JSON bodies are capped at 1 MiB, boat.dev file writes at about 7 MiB (5 MiB base64-encoded).
- **Scopes through `/api/v1`.** A compat route runs native handlers only within its caller's scopes: each native call checks the scope of the native route it runs, so `POST /api/v1/sandboxes/{id}/host` (and create's `hostedPorts`) needs `exec` like the native port URL does, and saving, deleting or sharing a saved snapshot needs `vms:read` too (it lists the team's snapshots). A unit test sends every `/api/v1` route a key of each single scope and fails if any native call ran without its scope.
- **Signed links at use.** A file download, upload or snapshot-chunk URL works only while its minting key exists, is unexpired, its user is still a member, and the key still holds the scope minting needed. Links a VM's own token mints (port, desktop and file URLs) die when that token's generation moves (create, start, fork, snapshot, share); its share codes live while the VM's token does; committed SSH self-grants retain their durable grant lifetime across token-generation rotation.
- **Webhook targets.** Deliveries dial only public addresses, checked after DNS on the address actually dialed: never private or special-purpose networks, never this host's own addresses (its public ones included, which reach services bound to loopback through a NAT rule), never a VM's `ip`, `ipv6` or `public_ip` as boatd reports them (refreshed every 10 s; a webhook fails closed while boatd cannot be read), and never the `-webhook-deny` CIDRs (repeatable: set the VM pool's public prefix there). Uploads go to an unlinked temp file on the data disk, not memory. The AI proxy still shares boat-api's process, so a flood of allowed requests costs the API's memory too.
- **State caps.** Per team: 200 secrets and 2 MiB of sealed secret values, 100 live shares, 4 MiB of environment scripts and vars, 200 ssh keys. The command history keeps 8 KiB of each argv.
- **Secrets.** `state.json` is sealed as a whole under the master key, because it holds environment vars, setup scripts, command lines and prompts. A plaintext file from an older version is sealed when boat-api opens it, and an older boat-api cannot read the sealed file, so do not roll back past this change. Tenant secrets and webhook keys are also sealed individually with AES-256-GCM under boat-api's master key. That key and the desktop/route HMAC key exist on disk only as systemd credentials (`/var/lib/boat/secrets/*.cred`, directory 0700 root), encrypted with the TPM2 when present plus the host key `/var/lib/systemd/credential.secret`, and handed to the services with `LoadCredentialEncrypted`. Plaintext keys from older installs are sealed, verified and deleted on upgrade. Backups contain only the sealed files, so **a backup alone cannot decrypt anything on another host. Keep offline copies:** `sudo systemd-creds decrypt --name=boat-master-key /var/lib/boat/secrets/boat-master-key.cred - | base64` (same for `boat-desktop-key`). API keys are stored as salted HMACs. Caddy's DNS token belongs in `gateway.environmentFile`.
- **Host hardening** comes from PandaOS: nftables, key-only ssh, sshguard, sysctl hardening, daily updates with health-check rollback.
- **Not defended:** a malicious server admin; side channels between VMs on shared cores (no core pinning, though `untrustedTenants` disables SMT); `Writeback` `fsync` stalls when a neighbour floods dirty pages into the shared host writeback queue (`untrustedTenants` enforces `blk-iocost` latency-targeted weights and per-VM `io.max` 4,000 MB/s / 200,000 IOPS ceilings, plus a 25% uplink share with fair queueing, which bound raw throughput/IOPS but do not isolate host page-cache writeback flushes); a full compromise of the host through a KVM or Firecracker bug (no second layer beyond the jailer); and abuse from your IPs beyond what your policy and quotas stop.

### Tenant model

- **Teams** own VMs, secrets, webhooks and keys. A key belongs to one user in one team and has scopes (`vms:read`, `vms:write`, `exec`, `admin`). Admins manage members and secrets.
- **Keys.** A key can list, rotate, delete or read usage of a key only if that key's scopes are within its own. Another user's key also needs the `admin` scope and a role no higher than the caller's, and only the operator can touch the operator's keys. Anything else is 404.
- **Deleting a team** also deletes its snapshots, imported ones included, and its AI usage rows (lifetime and per day, unflushed counts too).
- **Links die with their key.** Port links, file download and upload URLs, snapshot download chunks and snapshot share codes (`bsh_…`, with their `/v1/snapshot-links/…` URLs) stop working once the API key that minted them is deleted or expires.
- **VM self-tokens** (the key a VM gets for itself, `boat self`) cannot open public ports or add ssh keys to their own VM (403), so an agent talked into it cannot publish its VM or let someone in. A team admin can allow either with `PUT /v1/teams/{id}/self-token` `{"public_ports": true, "ssh": true}`; both are off by default.
- A team sees and reaches only its own VMs: API objects are filtered by team, nftables blocks other teams' VMs, jump grants list only the team's VM IPs, and every desktop link and route token is bound to one VM.
- **Secrets reach VMs only when chosen.** See [Secrets](#secrets).
- **Quotas** (`services.boat.quotas`, per-team overrides with `boatdSettings.teams`) cap running and total VMs, vCPU, memory, disk, snapshots and routes, all finite by default under `untrustedTenants` (the server profile's default); with `untrustedTenants = false` the VM, vCPU and memory caps default to 0 (host admission only). Metering (`/v1/usage`) records VM-seconds per size and snapshot-days per team. There is no billing.

### Secrets

Writing a team secret needs `admin`, and a VM's env is readable by anyone with `exec` on it, so a VM gets a secret only if:

- the request that creates it names the secret (`"secrets": [...]`, `boat new --secrets A,B`), and either the key is `admin` or the secret is default-injected (a member key naming any other secret is refused with 403), or
- its environment selects it (environments are written by admins), or
- the request names nothing and an admin marked the secret **default-injected**: `PUT /v1/secrets/{name}` with `"inject": true`, `boat secrets set NAME VALUE` (the CLI marks it, as boat.dev's CLI secrets go to every sandbox; `--no-inject` does not), or boat.dev's `POST /api/v1/secrets`.

A new secret set through the API is not default-injected; a rotation keeps the mark. `GET /v1/secrets` shows `inject`.

In a create's `secrets`, **absent means the default-injected secrets** (`@default`) and `[]` means none. A snapshot of unknown origin (an import, a share from another team that is not `@no_env`, a snapshot from before records were kept, a lost record, or a snapshot of a VM whose environment never landed) is judged as if it held every team secret: a create from it **cold-boots** (fresh boot, slower) unless its selection covers every team secret. The record of a snapshot of a VM holds the team secrets that VM's **run was started with** (the names pushed at its create, fork release or cold start, kept in the VM's run record), not the selection expanded when the snapshot is taken: a secret un-defaulted since the run began is still in it, so a create with the default selection then boots fresh. A VM whose run has no recorded names (a run from before they were kept, a lost write) gives a snapshot of unknown origin until its next start records them. A share **within the same team** keeps the sender's record; across teams only `@no_env` carries over.

**Environment builders.** The builder VM of an environment (label `boat.env`) holds the environment's secrets, so a key without scope `admin` gets 403 `forbidden` on everything but reading its metadata (`GET` of the VM, its usage, AI usage, snapshot list, ports and SSH grants, and revoking an SSH grant): start, stop, fork, delete, patch, resize, exec, commands, prompts, files, ports, SSH keys, desktop, snapshot create and download, native and `/api/v1`. Admin keys and the builder's own VM token are not refused. The **team-level snapshot routes** are gated the same way: `DELETE /v1/snapshots/{sid}`, `DELETE /api/v1/snapshots/{sid}`, `DELETE /api/v1/saved-snapshots/{name}` and `DELETE /api/v1/named-snapshots/{name}` answer 403 for a key without scope `admin` when the snapshot was taken from a builder VM or is an environment's build snapshot (`Environment.Build.SnapshotID`), and `POST /api/v1/saved-snapshots` (or `named-snapshots`) refuses, before it takes a new snapshot, to replace a same-name snapshot that is so protected. **Downloads and creates from such a snapshot are gated too:** `GET /api/v1/snapshots/{sid}/download` answers the builder 403 (and a chunk URL minted earlier is refused when it is fetched, if its snapshot became a build snapshot or its VM a builder meanwhile), and `POST /v1/vms` / `POST /api/v1/sandboxes` with `snapshot` / `from` naming such a snapshot is 403 for a key without `admin`; an environment's own build snapshot is still used through the environment (`environment`, or the default environment), which is how a member gets a built VM.

**A `no_env` sandbox's own token.** While a sandbox is `no_env` (sticky: from its first `no_env` start, create or fork), the VM's own token (`BOAT_API_KEY`, which a `no_env` run still receives) is limited to an **allowlist**; every other route is refused with 403 `forbidden`. Allowed: `GET` of its own VM (`/v1/vms/{id}`, compat `/sandboxes/{id}`); `exec`; starting commands (`POST …/commands`) and, for **commands started since the sandbox's latest `no_env` start**, their status (`GET …/commands/{cid}`; compat `…/commands/{pid}` and `…/stream`), logs, signal and stop/kill (`DELETE …/commands/{cid}`); the files of its own VM (`…/files` GET/PUT/DELETE, `files/list`, `move`, `search`, `find`, `info`, `folder`, `permissions`, `replace`, `download-url`, `upload-url`); `GET …/ai-usage`; and stopping itself (`POST …/stop`). Everything else is refused, notably snapshots (list, create, delete, download), command history and the logs, prompts, conversations and events of earlier runs: those hold the disk, memory and output of runs before the mark, which may carry team secrets the `no_env` start was made to withhold. A command addressed by id is readable only if it started at or after the mark (an unknown id is refused too), and the token may not change the VM's auto-stop, resize it or delete it. A key (not the VM's token) is not limited. **The refusal does not end with a stop or a plain start:** the sandbox stays `no_env`, so a new token generation minted by a later start is limited the same way. The restriction is also bound to the token generation, so exfiltrating a `no_env` token and stopping the VM with it opens nothing.

**`resume_on_boot`** is managed by the host (boatd sets it on a clean shutdown and restarts such VMs with no API checks): `PATCH /v1/vms/{id}` with `resume_on_boot` answers 400 `invalid_request` ("resume_on_boot is managed by the host") and changes nothing.

**Conversations** are kept per VM up to 200 (like prompts); the least recently updated one is dropped when a new one would pass that.

**Migration.** Before this, a VM created without a selection got every team secret at each start. VMs created from now on record the marker `@default` (in `state.json` and the `boat.secrets` label, which forks copy) and get only the default-injected secrets, read at each start. VMs created before the upgrade carry no selection record and keep their old behaviour (every team secret) until deleted; to stop that, recreate or fork them with an explicit selection, or delete the secrets they must not see. Environments without a selection now give their VMs and builds the default-injected secrets, not all. To keep today's behaviour for a secret, mark it: `boat secrets set NAME VALUE` (or `PUT /v1/secrets/NAME {"value":…, "inject":true}`). Tests: `TestSecretsAPIAndInjection`, `TestPerVMSecretSelection`.

The proxy forwards only inference endpoints; anything else is 403 before the team's key is read, so a VM token cannot reach a provider's files, batches, fine-tuning, assistants, admin or organization APIs. Paths are relative to the provider's upstream, `*` is one path segment; `.`/`..`/empty segments and encoded `/` or `.` are refused. Source: `components/boat/api/aiallow.go`; test: `TestAIProxyAllowlist`.

**Usage metering.** The proxy reads token counts from the answer (JSON body or SSE) and counts them per VM, provider, model and UTC day (`GET /v1/ai/usage`, compat `…/ai-usage`):

- *Streaming completions.* OpenAI-style providers (every provider but `anthropic`) report usage on a stream only when asked. For every `POST …/completions` (chat, legacy, FIM and agents paths; for `mistral` only `chat/completions`) whose body has `"stream": true`, the proxy sets `"stream_options": {"include_usage": true}` on the upstream request, **whatever the caller sent**: an own `include_usage` of `false` is overridden, and the body is re-encoded as one canonical JSON object, so duplicate keys cannot show the provider another value than the proxy saw. The stream then ends with one extra chunk with an empty `choices` array and a `usage` object, which clients written for the OpenAI API accept. The body's framing does not matter: a sized body, a chunked one (no `Content-Length`) and any `Content-Type` are read whole (up to 32 MiB; larger is refused with 413), patched and forwarded with a `Content-Length`. A body that is not a JSON object, or whose `stream` is present but not a boolean, is refused with 400 `invalid_request`. A body must arrive within 60 s and at no less than 64 KiB in every 10 s window (408 otherwise: a trickling body does not hold its bytes for a minute). Buffered bodies are charged **as their bytes arrive** (as buffer capacity, which doubles from 4 KiB), never by a declared `Content-Length` (a declared length over 32 MiB is refused with 413 at once), against a **128 MiB** global, a **32 MiB** per-team (a quarter of the global one, so at least four teams can hold their full budget at once) and a 32 MiB per-VM byte budget (the request really holds about 3x its bytes, so the global budget is at most ~384 MiB of real memory; the defaults were 256 and 96 MiB, ~768 MiB of real memory) (429 with `Retry-After` when the VM's or the team's is exhausted, 503 when the global one is: one team's VMs cannot use up the budget of the others). The bytes go back when the body has been written to the provider, not when the provider answers. A request holds about 3x its body in memory while it is patched. Residual: the global budget is four times the per-team one, so four teams can hold the whole global body budget and make a fifth team's bodies wait on 503 until theirs drain (team creation is operator-only, so this needs an operator-created set of colluding or compromised teams). `/v1/responses` and Anthropic-style streams carry usage already.
- *A client that hangs up* mid-stream no longer drops the final usage chunk: the proxy keeps reading the provider's answer into the meter, for at most 30 s and 8 MiB after the client left, and then cuts the upstream call. The call still ends at once when the VM's token or the team's credential is revoked. The provider is therefore billed for the whole answer, as it would be when the proxy forwards it all.
- *No usage object.* A successful (2xx) `POST` to a completions, messages, responses, embeddings or complete endpoint whose answer shows no usage (for example a request the proxy could not patch, such as a compressed body, or one whose client left and then the drain bound ran out before the usage chunk) is counted as a request with 0 tokens and flagged **unmetered**: `unmetered` on each row of `GET /v1/ai/usage` and `GET /v1/vms/{id}/ai-usage`, and in their `totals`, counts those requests (a subset of `requests`). boat-api also logs `ai proxy: unmetered response: vm … (no usage object seen)`. The boat.dev compat usage rows (`/api/v1/ai-usage`) have no such field. A line over 1 MiB in an SSE stream no longer hides the usage line after it: only that line's head and tail are read.
- *Durability.* Counts are batched in memory and moved into the state every 30 s; the disk write of that batch is lazy (coalesced, at most 5 s later, no fsync inline), and a usage read overlays the unflushed batch on the stored rows, so neither counting nor reading usage waits for a `state.json` fsync. On shutdown the meter flushes durably and `main` closes the store; any other durable state write also carries the batch. After a crash (kill -9, power loss) up to about 35 s of usage can be lost, and under-count by that much; nothing is ever counted twice.

## Upgrades and reboots

- **Updates.** The daily unattended update (`updates.nix`) switches to the new system with a health check and rolls back on failure. boatd is never restarted by a switch (`restartIfChanged = false`), so running VMs are untouched. boat-api, boat-gateway and Caddy restart in seconds; the API's clients retry.
- **Pending reboot.** `boat-reboot-check` (hourly) compares the booted kernel, initrd and modules, and boatd plus its config and Firecracker paths, with the installed ones. It logs `boat: reboot pending (changed: ...)`, writes `/run/boat/reboot-pending` and exports `boat_reboot_pending` (0/1) with a `reason` label.
- **Maintenance window.** With `maintenance.reboot = true`, a timer (`onCalendar`, default Sunday 04:00, ±10 min) applies what `boat-reboot-check` reports pending (`onlyWhenPending = false` acts every time). With `maintenance.action = "auto"` (default) a pending change of boatd or Firecracker only restarts `boatd.service`, and the host stays up; any other pending change (a new kernel) reboots. `action = "reboot"` always reboots. Both drain on their own: stopping boatd pauses and memory-snapshots every running VM (`stopTimeoutSec`), and the new boatd resumes them, with processes, tmux sessions and open files intact. TCP connections into VMs drop. `boat_maintenance_window_enabled` and `boat_maintenance_last_run_timestamp_seconds{action}` are exported for node-exporter.
- **Manual:** `sudo systemctl restart boatd` applies a new boatd without a reboot (VMs snapshot and resume); `sudo reboot` for a kernel.
- **Rollback:** pick the previous generation in the boot menu, or `sudo nixos-rebuild switch --rollback`. VM state on `/var/lib/boat` is independent of the system generation.

## Backups

`services.boat.backup` (restic, to a repository you provide):

1. Each run (default 03:00, `Persistent`) takes **read-only btrfs snapshots**: `/var/lib/boat` as `.backup/top`, and every nested subvolume (each VM's directory, with boatd's `btrfsQgroups`) as `.backup/sub/<path>`. A btrfs snapshot does not include nested subvolumes, so each one is snapshotted on its own. Each VM's disk and memory snapshot is crash-consistent; the API database and sealed master key come with `top`.
2. restic uploads the snapshots (images excluded; they are re-downloadable), the btrfs snapshots are deleted, and `pruneOpts` apply (7 daily, 4 weekly, 6 monthly).

Restore onto a fresh boat host (`checks.boat-ops` runs the restic restore into a scratch directory and the key recovery; it does not restart real VMs from a restore):
1. Stop boatd and boat-api.
2. `restic restore latest --target /tmp/r`, then copy `/tmp/r/var/lib/boat/.backup/top/.` and each `.backup/sub/<path>` back to `/var/lib/boat/<path>` (`cp -a --reflink=auto`).
3. Reseal both keys from your offline copies, because the `.cred` files in the backup open only on the old host: `base64 -d copy | sudo systemd-creds encrypt --with-key=auto --name=boat-master-key - /var/lib/boat/secrets/boat-master-key.cred`, and the same for `boat-desktop-key`.
4. Start boatd and boat-api again.

Test a restore before you need one.

## boat.dev API compatibility (`/api/v1`)

```python
from boat_sdk import ApiClient, BoatApi, Configuration
api = BoatApi(ApiClient(Configuration(host="https://api.boat.example/api/v1", access_token=KEY)))
```

```ts
const api = new BoatApi(new Configuration({ basePath: "https://api.boat.example/api/v1", accessToken: KEY }));
```

**Ids.** boat.dev's SDKs refuse a sandbox id that is not `bx_` + 8 characters of `23456789abcdefghjkmnpqrstuvwxyz`. Each VM gets one the first time `/api/v1` shows it: drawn at random, checked against every id in use, kept in `state.json` for the VM's life and dropped when it is deleted. Another team's id is 404. A native `vm-…` id also works in `/api/v1` paths.

**Envelope.** Success is `{"ok":true,"type":"…", …}`. Every error under `/api/v1` (auth, rate limits, validation, boatd) is `{"ok":false,"type":"sandbox.error","status","code","message","error":{"code","message","status","details?"},"requestId"}`, plus `retryAfterSeconds` on 503. Native codes are renamed where boat.dev has its own: `quota_exceeded` is `limit_reached`, `host_capacity` is `out_of_capacity`, upstream failures are `http_500`.

Compatibility sandbox responses (create, GET and list) resolve `environment` to the current name of the locally associated team environment and `environmentVersion` to the sandbox's retained pin. Legacy sandboxes without a pin report the current version they replay. Both fields are null for no-env sandboxes or a deleted/unknown environment; deleting an environment preserves existing pin variables for resume. The optional `access` field is omitted because creator identity is not recorded.

Environment upgrade is mapped. Snapshot trees and files would mean reading a tenant's disk image on the host, and there is no safe host-side parser for untrusted disk images; environment secret files have nothing to map onto, since the secrets store holds env vars only. No `X-Boat-Org`. `RateLimit` and `RateLimit-Policy` (IETF draft syntax, per key and per team bucket) are sent on create, fork and resume and on every rate-limit 429.

**Errors.** A refusal from the VM's own agent keeps its message and becomes a 4xx on `/v1` and `/api/v1` alike: an image without the feature (desktop on `slim`) is 422 `not_supported`, bad input 400, a session that exists 409; other guest failures are 502 with the guest's message. Under `/api/v1`, `code` is `http_<status>` for server-side failures, so it always agrees with `status`.

**CLI.** `boat` takes boat.dev's verbs next to its own: `boat extend <vm> --hours N | --ttl S | --no-auto-stop` (sets the time left, as boat.dev's) or `--by 2h` (pushes the deadline out), `boat limits`, `boat snapshot <vm> NAME` and `boat snapshot rm NAME`, `boat history <vm> [command-id] [-f]`, `boat webhook create URL --event ready … | list | rotate ID | remove ID`, `boat rename <vm> NAME`, `boat api-key create NAME [--preset read-only|full-sandbox|ci|admin | --actions a,b] | list | usage ID | rotate ID | revoke ID` (`--ttl 90d|24h|never`; `--sandbox` and `--env` are refused, as by the API), `boat status <vm>`, `boat events <vm>`, `boat recover <vm>`, `boat share <vm>`, `boat unshare <vm>` (both propagate 501 `not_supported`; no ports, tokens or teammate API/SSH access change), `boat dashboard [--no-open]` (the API's origin), `boat ssh-keys ls <vm> | rm <vm> FINGERPRINT`, `boat browser` (= `desktop`), `boat convos` (= `conversations`), `boat feedback` (where to file issues), `boat help [verb]` and `boat <verb> --help` (no login needed), `boat deletion status <operation id>`, and the global `--api-url URL` (boat.dev's flag, env `BOAT_API_URL`; a trailing `/api/v1` is dropped; this run only, `login --url` saves one). boat.dev's [In scripts and CI](https://docs.boat.dev/cli) pattern runs as is (`TestBoatDevScriptSnippet`): `boat new --json` prints the VM as one `{"event":"ready","id":…}` line, `boat delete ID --yes --json` takes `--yes`/`-y`, `prompt`/`events`/`conversations` print JSON Lines, and a `--json` failure ends stdout with `{"event":"error","error","code","status","message"}` (stderr keeps `{"error":{…}}`). **Snapshot grants to another team** (`POST /v1/vms/{id}/snapshots/{sid}/shares` with `team_id`) answer the same 201 whether or not that team exists. **pi, prime, kimi and mistral are untested.** Their flags were read from each CLI's `--help`; none of them has run here, in CI or by hand, and their output formats are unknown. boat-api passes their output through as is and looks for a session id with the same loose patterns as for codex and opencode; a turn whose output has none still runs, and the next turn in that conversation starts a new session. A `prime` prompt that starts with `-` gets a leading space, because its prompt is positional and no `--` is documented.

## Honest gaps

- **Unreviewed:** no external penetration test. See the status note at the top.
- **One host:** no HA, migration or cross-host scheduling.
- **No GPUs, and guest KVM is off by design** (Docker works). This deviates from boat.dev on purpose: guests get no `/dev/kvm`.
- **No guest is proven to survive a switch under NixOS.** Guests boot and survive a boatd restart under the NixOS server profile in an nspawn container on the runner (`boat-real guest`), not on a booted NixOS host; see "Not tested by anything" above.
- **No real agent run:** CI has no API keys, so agents are only exercised with a stub.
- **Windows CLI:** cross-compiled only, never run on Windows. `install.sh` and `boat upgrade` were not tested there.
- **Only partly API-compatible with boat.dev:** `/api/v1` maps 98 of boat.dev's 122 operations (see [boat.dev API compatibility](#boatdev-api-compatibility-apiv1)). the CI workflow covers the calls listed there on real VMs, while current local acceptance uses fake boatd; historical runs do not verify the changed contract on deployed infrastructure. Orgs, repos, CI, data retention and billing are not offered (501 `not_supported`); credential profiles are one `default` profile per team.
- **SSH UX** is `-J jump@… dev@<ip>` (wrapped by `boat ssh`).
- **Egress and disk QoS bounds:** SMTP is blocked by default, `untrustedTenants` configures a 25% per-VM uplink share with fair queueing (or `egressMbit` rate caps) plus `blk-iocost` disk weight sharing and per-VM `io.max` ceilings (4,000 MB/s, 200,000 IOPS), and private/special-purpose IPv4/IPv6 ranges are dropped on egress — but there is no cumulative per-team egress byte budget, no public-internet destination allowlist, and `Writeback` `fsync` latency still shares the host writeback queue across neighbours ([`cost.md`](cost.md#untrusted-disk-the-old-caps-and-what-replaced-them)).
- **The sealed keys** are bound to this host's TPM/host key. Keep the offline copies: without the master key a hardware change loses the whole API state (teams, keys, secrets, environments), and desktop and route links stop working.
- **`vmDomain` on the Public Suffix List** is an owner step, see checklist item 2. Until then a tenant page's script can set `Domain` cookies for sibling tenants.
- **The AI proxy** runs inside boat-api: per-VM limits bound it, but it has no process of its own. An open proxied stream (every 3 s) ends when its VM's token generation moves on, the VM is retired, blocked or loses its team, the team's credential for that provider is deleted or replaced, or the team switches the proxy off. Memory: a request body is read whole (to meter streaming usage), and a request holds about three copies of it at once (the read, the patched or re-encoded body, the forwarded one), so ~3x the body per in-flight request. Bodies are bounded by a byte budget: 128 MiB across all teams, 32 MiB per team, 32 MiB per VM and a body cap of 32 MiB by default (larger is refused with 413); the budgets count bytes received while a request holds about 3x its body, so the defaults are chosen for that (the global one bounds the real memory of buffered bodies near 384 MiB; it was 256 MiB, ~768 MiB, which charged the bytes once); the bytes are charged as they arrive (not by the declared `Content-Length`) and released once the body is written to the provider. A request that would exceed the per-VM or per-team budget is refused with 429 and one that would exceed the global budget with 503, both with `Retry-After`, rather than queued, and a body must arrive within a 60 s read deadline and at no less than 64 KiB per 10 s (408 otherwise). The upstream client keeps up to 64 idle connections per provider host (256 in all) and speaks HTTP/2 where the provider does, so bursts of VM requests reuse TLS connections. The upstream path is re-encoded segment by segment: an encoded `?` or `#` in an id (`%3F`, `%23`) stays part of the path and never becomes the provider's query or fragment.
- **The VM's own key** (`BOAT_API_KEY` in the guest, with `-vm-api-url`) reaches only that VM's routes, but anyone with a shell in the VM has it, and processes that read it before a rotation keep a dead one. See `components/boat/api/README.md`.
- **API latency:** VM token generations are intentionally fsynced to boat-api's `state.json` before publishing a new token or VM disk copy (fork, snapshot, share), so a copied token cannot become valid again after an API crash. Lifecycle calls that mint or rotate these tokens can wait for that write. Historically, boatbench 41652606509 measured 1.9 s of fsync in a 2.73 s new-from-snapshot while the disk was busy with snapshot writeback. `api/latency_test.go` checks a narrower configuration: an instant fake boatd without VM API tokens, under 100 ms of API time with a 300 ms fsync. Those measurements do not establish latency with durable token rotation; a fresh boatbench run has not measured it.
- **Guest images** are not pinned by default. Import them or set URLs and hashes in
  `services.boat.images`. See [Guest images](#guest-images).
- **Metrics:** host metrics and `boat_reboot_pending` only; per-VM numbers come from `/v1/usage`.

## Integration notes

- **Flake.** `services.boat` is in `nixosModules.default`, with `nixosModules.server`, `nixosConfigurations.server`, the `boat*` packages and `packages.iso-server` (headless live system that installs `headless` or `server`, built by `boat-e2e` and on release).
